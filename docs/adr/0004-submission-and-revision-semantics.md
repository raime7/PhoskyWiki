# 0004 - 提交与修订语义

- 状态：已接受（Accepted）
- 日期：2026-09-04
- 关联：Amends [0001-mvp.md](../specs/0001-mvp.md)「核心数据模型（submissions）」「提交状态机」「受理规则」三条；依赖 [ADR-0003](./0003-unified-page-shell-and-id-addressing.md)（修订挂 page_id）

## Context

spec 0001 初版写 submissions「含提案 diff 与状态」，两票制只留一行规则。实施前评审暴露四组未定义语义：(1) 两票边角——一准一驳是什么终态、恰两名管理员意见相反是否永久僵局；(2) 并发——两名编者基于同一旧版提交，后受理者如何避免静默覆盖；(3) 驳回后「修改再提」是改同一提交还是新建；(4) 回滚是恢复旧快照还是生成新修订。另有先例可援：XWiki 官方停止为历史存 diff（大文档成本高），改为全量存储、diff 展示时现算——diff 是展示期产物，不是存储形态。

## Decision

1. **submissions 存全量提议内容**，不存 diff；审核队列的「当前版 vs 提案」diff 在展示时现算。字段含：目标 page_id、提议内容、base_revision_id、状态、驳回理由、投票记录。
2. **并发防护**：提交必带 base_revision_id（编辑起点时的页面当前修订）。受理时若页面 head 修订 ≠ base_revision_id，该票无法通过——驳回并提示提交者基于新版重新提交（rebase）。
3. **两票语义 = 顺序批准、任一驳回即终态**：需要两票时，两名管理员先后批准即通过；任一管理员驳回，提交立即进入 rejected 终态（一准一驳 = 驳回），无僵局、无仲裁机制（冷启动期管理员个位数，分歧线下解决比状态机便宜）。驳回必填理由并通知提交者。
4. **quorum 在提交创建时快照**（`min(2, 当时管理员数)`），其后管理员人数变化不追溯影响已存在的提交。
5. **rejected 是终态**：修改后重新提交 = 新建一条 submission（可引用被驳回提交形成谱系，便于个人主页分组展示），不是复活旧提交。
6. **draft 在客户端**：编辑草稿 = localStorage 自动保存，服务端只见 pending 之后的提交；一期不建服务端草稿表。
7. **回滚 = 生成内容等于目标历史修订的新修订**（带 rollback 元数据指向来源修订），永不篡改或删除既有历史。
8. **生效触发面**：受理通过、管理员直编、回滚、软删除/恢复、改名（换 slug）都触发该页 links 重建与搜索索引同步（同步机制沿用 spec：事件驱动增量 + 定期全量校对）。
9. **统一修订管线**：管理员直编与回滚同样产生修订快照，与受理路径共用「产生修订 → 重建 links → 同步索引」，只是跳过排队与投票。

## Considered Options

- submissions 存 diff：被否——base 变化后 diff 作废，无法 rebase，也无法支撑「修改后重提」。
- 投票制 + 僵局仲裁（超时升级/第三方票）：被否——为冷启动期不存在的规模设计状态机；「任一驳回即终态 + 可重提」以最小规则消除僵局。
- 回滚 = 恢复旧快照指针：被否——破坏修订历史的线性与审计；「新修订内容等于旧版」保留完整因果链。

## Consequences

- submissions 表因存全量内容而变大（词条级文本量，PG 可承受；revisions 同理，沿用 spec 的全量快照决定）。
- 审核队列 UI 需要呈现 base 过期状态与「基于新版重新提交」入口。
- 两票制下先投批准票的管理员，在中途被驳回时其批准票随终态作废；投票记录保留展示即可。
- 「产生修订 → 重建 links → 同步索引」成为唯一写路径，测试围绕它展开（与 spec Testing Decisions 的主缝策略一致）。
