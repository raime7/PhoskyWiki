# Spec: 一期 MVP —— 词条 × 视角的原子笔记 WIKI

> 术语以 [CONTEXT.md](../../CONTEXT.md) 为准；需求全文见 [REQUIREMENTS.md](../../REQUIREMENTS.md)；技术约束见 [docs/TECH-STACK.md](../TECH-STACK.md) 与 ADR-0001/0002。
> 修订 2026-09-04：数据模型与提交/受理语义按 [ADR-0003](../adr/0003-unified-page-shell-and-id-addressing.md)、[ADR-0004](../adr/0004-submission-and-revision-semantics.md) 收紧（页面统一壳、id 寻址双链、提交存全量 + base 校验、任一驳回即终态）。

## Problem Statement

左翼哲学/政治经济学/历史的学习者面对的知识是散落的：同一概念（如"主体性"）在不同思想家体系里含义不同，现有百科把各派说法压平成一段中立叙述，读者既看不到"谁在什么立场上这么说"，也难以按自己的兴趣路径进入。同时，写作者缺少一个能把原子化笔记组织成体系、并与读者讨论直接衔接的场所。

## Solution

PhoskyWiki：每个词条是一个聚合枢纽，顶部是编委会的通俗视角，其下聚合各诠释者的视角页（原子知识单位）；词条轴 / 诠释者轴 / 学派轴三轴导航 + 双链 + 图谱让知识结构可视化；开放注册 + 两票审核制让社区安全共建；词条级讨论区衔接论坛；自带 BYOK 的 Agent 解读基于站内内容问答并生成阅读路径。

## User Stories

**内容与导航**

1. 作为读者，我想打开词条页先读到通俗视角，以便没有学科背景也能入门。
2. 作为读者，我想看到该词条下所有诠释者的视角列表（默认折叠露出 5~8 条 + 展开全部），以便概览各家分歧。
3. 作为读者，我想点击某诠释者进入其视角页，以便深入该体系对这个概念的完整诠释。
4. 作为读者，我想打开诠释者页看到人物信息框与其全部视角索引，以便系统地读一位思想家。
5. 作为读者，我想通过学派页浏览成员诠释者与学派核心词条，以便按流派学习。
6. 作为读者，我想通过分类树浏览词条，以便按主题找知识。
7. 作为读者，我想在同名多义词（如"价值"）上被消歧义页分流，以便不迷路。
8. 作为读者，我想看到红链标记未创建词条，以便发现写作缺口。
9. 作为读者，我想在词条页和视角页各看到反链面板，以便知道谁引用了它。
10. 作为读者，我想点击双链默认落到词条枢纽页，以便导航体验一致。
11. 作为读者，我想看到作者用显式语法精确链接到某视角的链接，以便直接跳到特定诠释。
12. 作为读者，我想看到信息框（infobox）里的结构化信息（领域、别名、关键文本等）。
13. 作为读者，我想在词条页看到局部图谱（1~2 跳邻居网络），以便直观理解概念的位置。
14. 作为读者，我想在全站图谱页缩放、拖拽、搜索定位节点，并按学派着色，以便鸟瞰整个知识体系。
15. 作为读者，我想在移动端获得同等可用的响应式界面。
16. 作为读者，我想在词条内看到图片（哲学家肖像、书影、图表）。

**搜索与发现**

17. 作为读者，我想搜索词条名、诠释者名、正文和讨论帖，并按类型分面过滤结果。
18. 作为读者，我想获得即打即搜的搜索联想。
19. 作为读者，我想在首页以大搜索为中心，配合编辑风陈列（本周概念/新视角/学派巡礼）作为门面。
20. 作为登录读者，我想在首页看到按我兴趣个性化的内容区块。

**兴趣与推荐**

21. 作为读者，我想选择兴趣标签（诠释者/学派/主题三类），以便获得个性化体验。
22. 作为未登录读者，我想兴趣标签存在浏览器本地（localStorage），以便不注册也有体验。
23. 作为登录编者，我想兴趣标签随账号同步，以便换设备不丢。
24. 作为读者，我想让词条下的视角列表按我的兴趣重排，以便最先看到最相关的诠释。
25. 作为读者，我想收到相关词条推荐，以便顺着兴趣扩展阅读。
26. 作为读者，我想获得跨词条的成套阅读路径，以便按体系学习。

**账号与审核**

27. 作为游客，我想用邮箱 + 密码注册成为编者。
28. 作为编者，我想登录与登出。
29. 作为编者，我想编辑既有词条/视角页并提交审核。
30. 作为编者，我想新建词条、视角页、诠释者页并提交审核。
31. 作为编者，我想收到审核结果（受理/驳回 + 理由）的站内通知。
32. 作为编者，我想在驳回后修改并重新提交，循环直到受理或放弃。
33. 作为编者，我想在个人主页查看我的提交历史。
34. 作为管理员，我想让自己的编辑不经审核直接生效。
35. 作为管理员，我想受理或驳回待审提交（非管理员提交需两个管理员受理；冷启动期按 min(2, 管理员数) 退化）。
36. 作为管理员，我想驳回时必须填写理由。
37. 作为管理员，我想对比任意两个历史修订（MediaWiki 式 diff 视图）。
38. 作为管理员，我想把页面回滚到任意历史修订。
39. 作为管理员，我想软删除页面（内容与历史全保留、可恢复）。
40. 作为管理员，我想直接上传图片，不经审核。
41. 作为管理员，我想用新建词条向导（骨架模板：信息框字段 + 通俗解读结构 + 视角占位 + 引用栏）起步。
42. 作为管理员，我想用结构化 JSON 批量导入词条与诠释者。

**讨论区**

43. 作为编者，我想在词条讨论区发表楼层并对他楼做一层嵌套回复。
44. 作为游客，我想只读讨论区（不可发言）。
45. 作为编者，我想在视角页一键"就这个视角发起讨论"，自动带视角锚点开楼。

**Agent 解读（BYOK）**

46. 作为 Agent 使用者（游客亦可），我想在浏览器本地配置 OpenAI 兼容端点（baseURL + key + 模型名），密钥永不上传服务器。
47. 作为 Agent 使用者，我想在页面侧栏发起基于当前词条 + 双链一跳邻居的问答，并流式看到回答。
48. 作为 Agent 使用者，我想让回答附带站内引用出处（可点击跳到词条/视角）。
49. 作为 Agent 使用者，我想让 Agent 生成阅读路径。

## Implementation Decisions

- 单体 Next.js（App Router），页面与 API 同仓；领域模块划分为：内容域（词条/视角/诠释者/学派/分类）、审核域（提交/受理/修订）、论坛域（讨论区）、发现域（搜索/兴趣/推荐/图谱）、Agent（纯前端 + 只读内容 API）。
- 核心数据模型（概念级，详见 ADR-0003）：pages 统一页面壳（type 判别 term/perspective/interpreter/school/disambiguation；title、slug、deleted_at；URL 形如 `/<type>/<slug>-<id>`，改名只换 slug、旧链接不断）；类型负载表挂 page_id——terms（词条，标题唯一，同名多义用括号限定标题）、interpreters（诠释者）、schools（学派，强类型实体只组织人）、perspectives（视角，词条 × 诠释者唯一约束；"编委会"为特殊诠释者，其通俗视角固定排第一）；categories（弱类型标签树只组织词条，一期不是页面类型）、revisions（修订，挂 page_id，每次受理产生一个全量快照，支持任意两版互比）、submissions（提交，存全量提议内容 + base_revision_id 与状态，详见 ADR-0004）、users（角色枚举 guest/editor/admin，预留 trusted）、links（source_page_id → target_page_id，保存时解析落库；target 可空 + target_name 文本快照即红链；图谱与反链与热度排序的共同数据源）、discussion threads/posts（词条级挂载，视角锚点可选）、interest tags（诠释者/学派/主题三类）、notifications（审核结果）、images（R2 对象元数据）。
- 提交状态机（详见 ADR-0004）：draft（客户端 localStorage 草稿，不落服务端）→ pending → approved | rejected（均为终态；任一驳回即 rejected）。修改后重新提交 = 新建提交；受理时校验 base_revision_id，页面已前进则驳回并提示基于新版重新提交。
- 受理规则：非管理员提交需提交创建时快照的 min(2, 管理员数) 张批准票（顺序批准，任一驳回即终态，无僵局无仲裁）；管理员本人提交直接生效（修订历史 + 回滚兜底）；驳回必填理由并通知提交者。回滚 = 生成内容等于目标修订的新修订，永不篡改历史。
- 页面删除一律软删除（pages.deleted_at），内容与历史保留。
- 视角列表排序：通俗视角第一 → 编者置顶若干 → 其余按站内引用数（links 统计）热度；用户设有兴趣标签时同一列表按兴趣重排。
- 双链语法：默认 `[[词条名]]` 落词条枢纽；显式 `[[词条名|视角@诠释者]]` 精确落视角页。解析发生在保存（受理产生修订）时，links 落目标 page_id——词条改名不断链；未创建词条 target 为空、按名称快照渲染为红链（写作缺口视图即未解析目标聚合）。
- 内容唯一格式为 Markdown 源文本；渲染管线基于 unified/remark 扩展 wiki-link；编辑器 CodeMirror 6 + 实时预览 + 双链自动补全。
- Meilisearch 为派生索引（ADR-0002）：生效事件（受理、管理员直编、回滚、软删除/恢复、改名）驱动增量同步 + 定期全量校对；PG 是唯一内容 source of truth（ADR-0001）。
- 图片经 R2 预签名直传（不经过应用服务器），元数据入 PG；禁用外链图。
- Agent BYOK：浏览器 fetch 直连用户配置的 OpenAI 兼容端点，SSE 流式渲染；问答上下文 = 当前词条 + 一跳邻居的渲染文本；引用以站内链接回填。
- 图谱：由 links 表聚合出节点/边数据的只读端点；前端 ECharts graph 渲染局部与全站两档。
- 认证 better-auth（邮箱密码、数据库会话）；通知一期仅审核结果站内通知。

## Testing Decisions

- 好测试只断言外部行为（HTTP 响应、渲染出的 DOM、纯函数输出），不断言内部实现细节。
- 主缝 = HTTP 边界（route handlers + SSR 页面），全站唯一主缝：
  - Playwright（真实浏览器）覆盖关键用户流：注册 → 提交 → 受理 → 内容可见；双链点击落点（枢纽/精确视角/红链）；登录态与权限。
  - Vitest 集成测试直接调用 route handlers：提交状态机与两票受理规则（含冷启动退化）、任意两修订对比、软删除与回滚、视角排序与兴趣重排。
- 纯函数单元测试（无 IO 的补充层）：wiki-link 渲染器、修订 diff 计算、视角排序函数。
- 测试用真实 PostgreSQL（docker，跑 drizzle 迁移），不 mock 数据库。
- Meilisearch 与 R2 各藏在单一接口（SearchIndex / ObjectStore）之后：主缝测试用 fake；各保留一条契约测试打到真服务。

## Out of Scope

- 需求文档列明的全部二期项：免审编者晋级层、论坛卡片嵌入与 SSO、全站 RAG、Agent 草稿生成与待审核队列、图谱高级过滤（分类剪枝/热度缩放）、讨论回复通知、全站数据导出 dump、视频等多媒体。
- UI 高保真视觉打磨（video2code 原型另行推进）：本 spec 只锁定信息结构与行为。
- 生产部署与 VPS 采购：Docker Compose 拓扑按 TECH-STACK.md，但不在本 spec 验收范围。

## Further Notes

- 全部术语（词条/视角/诠释者/编者/编委会/学派/分类/修订/提交/受理/回滚/兴趣标签/阅读路径/讨论区/图谱/Agent 解读）以 CONTEXT.md 的定义为准，代码命名与之一致。
- 三领域（哲学/政经/历史）统一视角模型，差异只体现在信息框模板与分类树。
- 首发内容由管理员从零撰写 50~100 个核心词条；中文正文 + 原文关键术语括号引用。
